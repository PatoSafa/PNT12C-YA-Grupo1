Guía completa: levantar, probar y desplegar una aplicación Spring Boot

Desde el proyecto local hasta una aplicación publicada en un servidor como Render.

1. ¿Qué vamos a construir?

La idea es que el alumno pueda tener una aplicación funcionando de punta a punta:

  • Una vista con index.html.
  • Un backend Spring Boot que expone endpoints.
  • Una base de datos MySQL, inicialmente ejecutada con Docker.
  • Comunicación entre la vista y el backend mediante fetch().
  • Un repositorio en GitHub.
  • Finalmente, un ejemplo de despliegue del backend en un servidor como Render.
Idea central: en desarrollo todo puede ejecutarse en la computadora del alumno. En producción, la aplicación debe ejecutarse en un servidor accesible por Internet y la configuración debe adaptarse al entorno del servidor.

2. Estructura de carpetas

Para una aplicación Spring Boot que sirve una página HTML estática, una estructura simple puede ser:

primerMvc/
├── pom.xml
├── src/
│   └── main/
│       ├── java/
│       │   └── ort/
│       │       └── edu/
│       │           └── ar/
│       │               └── primerMvc/
│       │                   ├── PrimerMvcApplication.java
│       │                   ├── controller/
│       │                   │   └── MyFirstController.java
│       │                   ├── model/
│       │                   │   └── Elemento.java
│       │                   └── repository/
│       │                       └── ElementoRepository.java
│       │
│       └── resources/
│           ├── application.yaml
│           └── static/
│               └── index.html
│
└── .gitignore
Importante: si index.html está dentro de src/main/resources/static/, Spring Boot puede servirlo como contenido estático. La URL local será normalmente http://localhost:8080/, si la aplicación usa el puerto 8080.
No confundir carpetas: el HTML no debe colocarse dentro de src/main/java. Para este ejemplo se utiliza src/main/resources/static.

4. Variables que deben estar configuradas

En el entorno local del ejercicio se pueden utilizar estos valores:

VariableValor local¿Para qué sirve?
Host MySQLlocalhostIndica que MySQL está en la computadora.
Puerto MySQL3306Puerto utilizado para acceder a MySQL.
Base de datosclaseNombre de la base.
UsuarioalumnoUsuario de conexión.
ContraseñaalumnoContraseña del usuario.
Puerto Spring Boot8080Puerto donde queda disponible el backend.

En application.yaml:

server:
  port: 8080

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/clase
    username: alumno
    password: alumno

  jpa:
    hibernate:
      ddl-auto: update
    show-sql: true
Atención: el puerto 3306 corresponde a MySQL. El puerto 8080 corresponde a Spring Boot. Son servicios diferentes.

5. Levantar MySQL con Docker

Desde la carpeta donde se encuentra el archivo compose.yaml o docker-compose.yml, ejecutar:

docker compose up -d

Comprobar que el contenedor está funcionando:

docker ps

La configuración utilizada en el ejercicio puede ser:

services:
  mysql:
    image: mysql:8.4
    container_name: mysql-clase
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: clase
      MYSQL_USER: alumno
      MYSQL_PASSWORD: alumno
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql

volumes:
  mysql_data:

7. Levantar Spring Boot localmente

Paso 1. Abrir el proyecto en IntelliJ IDEA.
Paso 2. Verificar que MySQL esté funcionando en Docker.
Paso 3. Verificar el application.yaml.
Paso 4. Ejecutar la clase principal: 
PrimerMvcApplication.java
que contiene el método main y la anotación @SpringBootApplication.
Paso 5. Esperar en la consola de IntelliJ hasta que Spring Boot termine de iniciar.
Paso 6. Abrir el navegador y entrar a: 
http://localhost:8080/
Si todo está correctamente configurado, debería aparecer el index.html.

8. ¿Por qué no alcanza con abrir el index.html haciendo doble clic?

Un archivo HTML puede abrirse directamente desde el explorador de archivos. Sin embargo, para este proyecto conviene que la vista sea servida por Spring Boot.

De esta manera, la arquitectura queda:

Navegador
    |
    | HTTP
    v
Spring Boot :8080
    |
    | API REST
    v
MySQL :3306

Además, la vista y el backend quedan dentro de una misma aplicación durante el desarrollo, lo que simplifica el flujo para los alumnos.

9. Conectar la vista con el backend

Supongamos que el backend tiene un endpoint:

GET /elementos

Desde el index.html podemos consumirlo con JavaScript:

<script>
  fetch("/elementos")
    .then(response => response.json())
    .then(data => {
      console.log(data);
    })
    .catch(error => {
      console.error("Error:", error);
    });
</script>
Ventaja de usar una URL relativa: si el HTML y el backend están siendo servidos por la misma aplicación, fetch("/elementos") apunta al mismo servidor que entregó el HTML. No hace falta escribir http://localhost:8080 en cada llamada.

Por ejemplo, si el servidor está en:

http://localhost:8080/

entonces:

fetch("/elementos")

equivale a solicitar:

http://localhost:8080/elementos

10. Flujo completo en local

  1. Encender Docker Desktop.
  2. Ejecutar MySQL con docker compose up -d.
  3. Comprobar el contenedor con docker ps.
  4. Abrir el proyecto en IntelliJ.
  5. Verificar application.yaml.
  6. Ejecutar Spring Boot.
  7. Abrir http://localhost:8080/.
  8. Comprobar que aparece el index.html.
  9. Probar los endpoints con Postman.
  10. Probar desde el HTML las llamadas mediante fetch().

11. Subir el proyecto a GitHub con Git Bash

Abrir Git Bash dentro de la carpeta del proyecto.

Comprobar Git:

git --version

Comprobar el estado:

git status

Agregar los cambios:

git add .

Crear el commit:

git commit -m "Agrega pagina de inicio y configuracion"

Subir a GitHub:

git push
No subir secretos reales: contraseñas, claves privadas, tokens y credenciales de producción no deberían quedar escritos en el repositorio.

12. ¿Qué cambia cuando pasamos de local a producción?

En local tenemos algo similar a:

Navegador
   |
   v
localhost:8080
   |
   v
Spring Boot
   |
   v
localhost:3306
   |
   v
MySQL Docker

En producción, la aplicación se ejecuta en un servidor remoto:

Usuario
   |
   | Internet
   v
Servidor / plataforma cloud
   |
   v
Spring Boot
   |
   v
Base de datos de producción
Importante: localhost siempre significa "esta máquina". Por eso, una configuración que funciona en la computadora del alumno no necesariamente funciona igual cuando la aplicación se ejecuta en un servidor.

13. Ejemplo de despliegue utilizando Render

Render puede utilizarse como ejemplo de plataforma cloud para desplegar una aplicación web. El flujo general es:

Código local
    |
    v
GitHub
    |
    v
Render
    |
    v
Aplicación Spring Boot publicada

El ejemplo supone que el proyecto ya está en GitHub y que puede construirse correctamente con Maven.

Paso 1 — Preparar el proyecto

Antes de desplegar:

  • El proyecto debe compilar correctamente.
  • pom.xml debe estar en la raíz.
  • La aplicación debe poder iniciarse correctamente.
  • El código debe estar subido a GitHub.

Paso 2 — No fijar obligatoriamente el puerto 8080 en producción

En un entorno cloud, la plataforma puede proporcionar el puerto mediante una variable de entorno. Por eso es conveniente configurar Spring Boot para utilizar PORT cuando exista:

server:
  port: ${PORT:8080}

Esto significa:

  • Si existe la variable PORT, se utiliza su valor.
  • Si no existe, se utiliza 8080.

Paso 3 — Crear el servicio web en Render

  1. Ingresar a Render.
  2. Crear un nuevo servicio web.
  3. Conectar la cuenta/repositorio de GitHub.
  4. Seleccionar el repositorio del proyecto.
  5. Configurar el entorno de construcción.
  6. Indicar el comando para construir la aplicación.
  7. Indicar el comando para iniciar Spring Boot.
  8. Realizar el deploy.

Ejemplo conceptual de comandos Maven

Build:
./mvnw clean package -DskipTests

Start:
java -jar target/primerMvc-0.0.1-SNAPSHOT.jar
El nombre exacto del archivo .jar depende del proyecto. Revisar el nombre generado dentro de la carpeta target.

Paso 4 — Configurar las variables de entorno

En producción no conviene utilizar las credenciales locales del ejemplo. La base de datos debe ser una base accesible desde el servidor y sus credenciales deben configurarse mediante variables de entorno.

Un esquema posible es:

DB_HOST
DB_PORT
DB_NAME
DB_USER
DB_PASSWORD

Y el application.yaml puede leerlas:

server:
  port: ${PORT:8080}

spring:
  datasource:
    url: jdbc:mysql://${DB_HOST}:${DB_PORT}/${DB_NAME}
    username: ${DB_USER}
    password: ${DB_PASSWORD}

  jpa:
    hibernate:
      ddl-auto: update
Concepto importante: la aplicación no debería depender de localhost:3306 para la base de datos cuando está desplegada en Internet. El host de la base será el servidor o servicio de base de datos correspondiente al entorno de producción.

14. ¿Y el index.html cuando se despliega?

Si el archivo continúa ubicado en:

src/main/resources/static/index.html

Spring Boot puede servirlo desde la aplicación.

En local:

http://localhost:8080/

En producción:

https://DOMINIO-ASIGNADO-POR-LA-PLATAFORMA/

La dirección exacta dependerá del dominio que proporcione la plataforma.

La ventaja de mantener el index.html dentro de static es que, en este ejemplo, la vista viaja junto con la aplicación Spring Boot.

15. ¿Qué pasa con fetch() en producción?

Si la vista y el backend están en la misma aplicación, conviene mantener:

fetch("/elementos")

en lugar de:

fetch("http://localhost:8080/elementos")

La primera opción se adapta automáticamente al dominio desde el cual se está ejecutando la aplicación.

Por ejemplo:

Local:
http://localhost:8080/elementos

Producción:
https://mi-aplicacion.example/elementos

El código JavaScript puede seguir siendo:

fetch("/elementos")

17. Errores frecuentes

La página no abre en localhost:8080

  • Spring Boot no está iniciado.
  • El puerto 8080 está ocupado.
  • La aplicación tiene un error de configuración.
  • index.html no está dentro de resources/static.

Spring Boot no conecta con MySQL

  • El contenedor MySQL no está iniciado.
  • El puerto 3306 está ocupado o mal configurado.
  • El nombre de la base no coincide.
  • El usuario o contraseña no coinciden.
  • La URL JDBC está mal escrita.

El fetch devuelve error

  • El endpoint no existe.
  • La URL es incorrecta.
  • El backend no está iniciado.
  • El endpoint devuelve un error del servidor.
  • Si frontend y backend están separados, puede existir un problema de CORS.

Funciona localmente pero falla al desplegar

  • Se está usando localhost para una base que no está en el mismo servidor.
  • El puerto no está configurado para el entorno cloud.
  • Faltan variables de entorno.
  • El comando de build o start es incorrecto.
  • El archivo JAR generado tiene otro nombre.

20. Idea que deben llevarse

El objetivo no es solamente "hacer que funcione". El alumno debe poder identificar qué componente está ejecutando cada parte de la aplicación:

  1. HTML/JavaScript: interfaz y comunicación con el backend.
  2. Spring Boot: servidor y lógica de backend.
  3. API REST: comunicación entre la vista y el backend.
  4. MySQL: persistencia de datos.
  5. Docker: ejecución local de la base de datos.
  6. GitHub: almacenamiento y versionado del código.
  7. Render: ejemplo de ejecución de la aplicación en un entorno cloud.
Objetivo final: poder pasar de index.html → Spring Boot → MySQL funcionando en la computadora, a una aplicación publicada mediante un servicio cloud, comprendiendo qué configuración cambia entre ambos ambientes.
