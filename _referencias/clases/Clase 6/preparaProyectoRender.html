PrimerMvc: preparar el proyecto para Render

Guía paso a paso para pasar de Docker + MySQL local a un despliegue en Render

1. ¿Qué tenemos actualmente?

El repositorio PrimerMvc tiene el proyecto Maven dentro de la carpeta primerMvc.

PrimerMvc/
└── primerMvc/
    ├── pom.xml
    ├── mvnw
    └── src/
        └── main/
            ├── java/
            └── resources/
                ├── application.yaml
                └── static/
                    └── index.html

Actualmente utiliza Java 17, Spring Boot, Spring Data JPA y MySQL.

Problema principal: application.yaml apunta a jdbc:mysql://localhost:3306/first. En Render, localhost no representa tu computadora ni el MySQL de Docker.

2. Objetivo

EntornoAplicaciónBase de datos
LocalSpring BootMySQL en Docker
RenderSpring BootPostgreSQL de Render
Importante: no vamos a romper el entorno local. La aplicación tendrá una configuración para Docker/MySQL y otra para producción.

3. Paso 1 — Agregar PostgreSQL

En pom.xml hay actualmente una dependencia para MySQL. Para producción agregaremos PostgreSQL.

<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>

El driver de MySQL puede mantenerse si queremos seguir ejecutando el proyecto localmente con Docker.

4. Paso 2 — Separar local y producción

Crear:

src/main/resources/
├── application.yaml
├── application-local.yaml
└── application-prod.yaml

application-local.yaml

spring:
  datasource:
    url: jdbc:mysql://localhost:3306/first
    username: root
    password: root
    driver-class-name: com.mysql.cj.jdbc.Driver

  jpa:
    hibernate:
      ddl-auto: update
    show-sql: true

application-prod.yaml

spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
    driver-class-name: org.postgresql.Driver

  jpa:
    hibernate:
      ddl-auto: update
    show-sql: false

Así, los datos de producción no quedan escritos directamente en el código.

5. Paso 3 — Configurar application.yaml

El archivo principal puede contener la configuración común:

spring:
  application:
    name: primerMvc

server:
  port: ${PORT:8080}

PORT será proporcionado por Render. Si no existe, Spring utilizará 8080.

En Render configuraremos:

SPRING_PROFILES_ACTIVE=prod

6. Paso 4 — Variables de entorno

En lugar de guardar credenciales en GitHub, Spring las recibe mediante variables de entorno.

VariableContenido¿Subir al repositorio?
DB_URLURL JDBC de PostgreSQLNO
DB_USERNAMEUsuario de la baseNO
DB_PASSWORDContraseñaNO
SPRING_PROFILES_ACTIVEprodSe configura en Render
Nunca subir contraseñas reales a GitHub.

7. Paso 5 — Verificar Maven

El proyecto ya tiene el plugin de Spring Boot y Java 17. Antes de desplegar hay que comprobar el build.

mvnw.cmd clean package

En Linux/macOS:

./mvnw clean package

Debe generarse un JAR en target/.

8. Paso 6 — Probar primero en local

  1. Levantar MySQL con Docker.
  2. Verificar la base first.
  3. Activar el perfil local.
  4. Ejecutar Spring Boot.
  5. Probar el login.
  6. Probar los endpoints de componentes.
SPRING_PROFILES_ACTIVE=local

O:

mvnw.cmd spring-boot:run -Dspring-boot.run.profiles=local
Si la versión local funciona, recién entonces conviene pasar a Render.

9. Paso 7 — Crear PostgreSQL en Render

  1. Entrar a Render.
  2. Crear una instancia PostgreSQL.
  3. Guardar los datos de conexión.
  4. Utilizar esos datos para configurar el Web Service.
La aplicación Spring Boot y PostgreSQL son servicios separados que se comunican mediante la conexión JDBC.

10. Paso 8 — Crear el Web Service

Conectar Render con el repositorio de GitHub.

Root Directory es importante: el pom.xml está dentro de primerMvc, no en la raíz del repositorio.

11. Paso 9 — Configurar variables en Render

En Environment Variables del Web Service:

SPRING_PROFILES_ACTIVE=prod
DB_URL=jdbc:postgresql://...
DB_USERNAME=...
DB_PASSWORD=...

Los valores reales se obtienen de la base PostgreSQL creada en Render.

12. Paso 10 — Revisar el frontend

El frontend está en:

src/main/resources/static/index.html

El login actual utiliza:

url: "/login"

Eso es correcto para producción porque es una ruta relativa.

No debemos convertirlo en:

url: "http://localhost:8080/login"

Las APIs también deberían utilizar rutas relativas como /api/componente.

13. Paso 11 — ¿Hace falta render.yaml?

No es obligatorio para el primer despliegue. Podemos configurar Render desde su panel.

Más adelante se puede agregar un render.yaml para documentar la infraestructura como código.

services:
  - type: web
    name: primermvc
    runtime: java
    rootDir: primerMvc
    buildCommand: ./mvnw clean package
    startCommand: java -jar target/primerMvc-0.0.1-SNAPSHOT.jar

La configuración definitiva de base de datos y variables debe adaptarse a los servicios concretos creados en Render.

14. Paso 12 — Probar el despliegue

  1. Esperar que termine el build.
  2. Abrir la URL pública de Render.
  3. Verificar que aparezca el login.
  4. Probar una autenticación.
  5. Probar las operaciones de componentes.
  6. Revisar los logs si aparece un error.

16. Orden de trabajo recomendado

  1. Agregar PostgreSQL al pom.xml.
  2. Crear perfiles local y prod.
  3. Dejar MySQL/Docker para local.
  4. Usar variables de entorno para producción.
  5. Probar localmente.
  6. Hacer commit y push.
  7. Crear PostgreSQL en Render.
  8. Crear Web Service.
  9. Configurar Root Directory = primerMvc.
  10. Configurar Build y Start.
  11. Configurar variables de entorno.
  12. Desplegar y probar.

19. Concepto que deben aprender los alumnos

Desplegar una aplicación no significa simplemente subir el código. Hay que adaptar la configuración al ambiente donde se ejecutará.

  • Configuración por ambiente: local y producción pueden utilizar bases diferentes.
  • Variables de entorno: permiten separar secretos y configuración del código.
  • Servicios: la aplicación y la base de datos son componentes independientes.
